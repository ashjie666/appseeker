## 1. 产品概述

### 1.1 背景与问题

小程序生态已形成微信、支付宝、抖音、百度、快手、QQ 等多平台并立格局，各平台陆续发布小程序「排行榜 / 热度榜」；同时 **HTML5 网页小游戏**（免安装、即点即玩）在各类聚合页 / H5 游戏分发站上形成独立榜单，是同一批用户与同一套「需求已验证、体验待改善」逻辑下的重要旁支。但现状存在三个结构性缺口：

1. **口径割裂**——各平台排名算法、下载/使用量统计口径、评价体系互不统一，跨平台无法直接比较。
2. **只看头部**——榜单只展示「表现好」的应用，掩盖了**流量高但口碑差**的反差样本。
3. **没有历史**——榜单多为实时快照，缺少可回溯的趋势数据，无法判断变化。

而真正高价值的信息恰恰藏在反差里：**「高下载 + 低好评」通常意味着需求已被验证、但体验尚未被满足**——既是可切入的替代机会，也是竞品流失风险的预警信号。

### 1.2 产品目标与成功指标

**北极星目标：** 每天稳定产出「高热度低好评」候选清单，帮助用户在 **3 分钟内**定位到值得关注的「需求强、体验差」机会。

| 指标 | 目标值 |
|---|---|
| 覆盖平台数 | ≥ 3（MVP，含 HTML5 网页小游戏）→ ≥ 5（阶段二），≥ 15 个品类榜单 |
| 更新频率 | **每日 2 次**（07:00 / 19:00） |
| 每日任务成功率 | ≥ 99% |
| 首页首屏加载 | < 2s（P95） |
| 反差名单人工抽检准确率 | ≥ 80% |
| 核心字段完整率 | ≥ 98% |

**明确非目标：** 不自建小程序本体、不采集用户个人画像、不提供投资建议。

### 1.3 核心用户

| 用户类型 | 画像 | 核心诉求 | 频次 |
|---|---|---|---|
| 独立开发者 / 小团队 | 1–5 人，寻找可切入赛道 | 发现「需求强、体验差」的可替代机会 | 每日 |
| 产品经理 / 竞品分析 | 互联网公司 PM | 跨平台竞品表现与口碑对比 | 每周 2–3 次 |
| 投资 / 行研分析师 | VC、行研 | 量化赛道热度与口碑走势 | 每周 |
| 小程序运营 / ASO | 增长从业者 | 自身诊断与竞品对标 | 每日 |
| 自媒体 / 数据爱好者 | 内容创作者 | 选题灵感与数据素材 | 不定期 |

### 1.4 使用场景

- **场景 A · 每日选品（独立开发者）**：早上打开首页，默认按「机会指数」看反差榜，筛选「微信 + 工具类 + 下载量 Top 20%」，3 分钟挑出 2–3 个方向。
- **场景 B · 竞品预警（产品经理）**：发现某竞品下载量周环比 +180%，但好评率从 88% 跌至 65%，判断其增长不可持续。
- **场景 C · 赛道研究（分析师）**：导出某品类近期快照，看反差名单的品类分布与趋势。
- **场景 D · 自身诊断（运营）**：把自家小程序放进榜单横比，定位「下载进前 15% 但好评率低于品类均值」的体验短板。

### 1.5 核心价值与差异化

| 价值维度 | 说明 |
|---|---|
| 效率价值 | 把「逐平台翻榜 + Excel 手工归一」的数小时工作，压缩为一次秒级筛选 |
| 洞察价值 | 用「下载热度 ×（1 − 好评率）」的缺口信号，发现被头部榜单掩盖的机会与风险 |
| 一致性价值 | 统一异构口径、量纲与命名，跨平台可比；估算值明确标记，避免误导 |
| 时间价值 | 每日 2 次快照沉淀，形成可回溯的榜单时间序列 |

**差异化定位：** 现有榜单是**正向展示**（告诉你谁最火）；AppSeeker 是**反向洞察**（告诉你谁火但没做好）。

## 3. 数据模型

### 3.1 设计原则

- **分层建模**：维度（dim）/ 事实（fact）/ 映射（map）/ 配置（config）/ 日志（log）。
- **快照式事实**：每次抓取按「时间点 + 平台 + 小程序」存一行，天然形成时间序列。
- **可追溯**：保留 `source_url`、`crawl_at`，任何一条数据都能追到来源。
- **可解释**：同时保留平台原始展示值与归一估算值，并标记是否估算。

### 3.2 实体关系

```
dim_platform 1───n fact_ranking_snapshot n───1 dim_app
dim_app      1───n map_app_platform      n───1 dim_platform
dim_app      1───n fact_app_score_daily
dim_app      1───n map_app_tag           n───1 dim_tag
dim_platform 1───n log_crawl_job
```

### 3.4 关键字段标准化规则

- **下载量归一**：`download_display` 保留原文；`download_est` 取区间下界估算并置 `is_estimated = true`。映射：`<1万 → 1e4`、`5万+ → 5e4`、`10万+ → 1e5`、`100万+ → 1e6`、`1000万+ → 1e7`。
- **量纲口径（metric_label）**：字段名沿用 `download_*`，语义随平台 `metric_label` 变化 —— 小程序为「下载量」，HTML5 网页小游戏为「游玩次数」。**首页**为多平台混合语境，展示统一使用中性词「**热度**」（热度量级 / 热度门槛 / 热度 × 好评率象限图）；**详情页**为单一平台，按该平台 `metric_label` 显示精确量纲（如「估算游玩次数」）。跨平台比较只使用相对分位 `download_pctl`，不直接比较绝对量纲。
- **好评率**：优先「好评数 / 评价总数」；若平台只给平均分，用 `rating_avg` 近似并标记 `derived`。
- **名称归一**：trim + 全角转半角 + 去冗余括号 + 别名映射。
- **时间统一**：全部 Asia/Shanghai；`stat_time` 为本次更新的时间点。
- **唯一性**：`(platform_code, platform_app_id, stat_time)` 唯一，保证幂等。

## 4. 「高下载低好评」筛选与评分逻辑

赢的公式：**下载热度 × 口碑缺口**。只有「又火」且「口碑差」才会得分高。

### 4.1 关键指标定义

| 指标 | 定义 | 说明 |
|---|---|---|
| `download_pctl` | 同一「平台 × 品类 × 时间点」内 `download_est` 的百分位（0–1） | **相对分位**而非绝对值，消除平台量级差异 |
| 高下载 | `download_pctl ≥ 0.80`（默认） | 可调 P50 / P80 / P90 |
| `positive_rate` | 好评数 / 评价总数 | 0–1 |
| 低好评 | `positive_rate ≤ 0.70`（默认） | 阈值可配置 |
| 样本量门槛 | `rating_total ≥ 100` 且 `comment_count ≥ 30` | **抑制小样本噪声**与刷评 |

### 4.2 阈值分档

| 档位 | 下载量 | 好评率 | 样本量 | 定位 |
|---|---|---|---|---|
| 宽松 | ≥ P50 | ≤ 0.75 | ≥ 50 | 广撒网探索 |
| **标准（默认）** | **≥ P80** | **≤ 0.70** | **≥ 100** | 平衡覆盖与置信度 |
| 严格 | ≥ P90 | ≤ 0.65 | ≥ 300 | 高置信度机会 |

### 4.3 综合评分公式

```
norm(x, lo, hi) = clamp((x − lo) / (hi − lo), 0, 1)

热度分 HeatScore = 100 × ( 0.60·download_pctl
                         + 0.25·rank_score
                         + 0.15·norm(ln(1+comment_count)) )
        其中 rank_score = 1 − (rank_no − 1) / N      # N 为该榜条数

口碑分 RepScore  = 100 × ( 0.60·positive_rate
                         + 0.25·norm(rating_avg, 0, 5)
                         + 0.15·(1 − neg_ratio) )

综合机会指数 OpportunityScore = 100 × download_pctl × (1 − positive_rate) × confidence
        其中 confidence = min(1, rating_total / 500)
```

> `OpportunityScore` 的本质是**「热度 × 口碑缺口」的乘积**，取值 0–100，越大越值得关注。乘 `confidence` 让样本充足的对象更靠前，避免「1 条差评即 0 好评」的小样本被误判。

### 4.4 筛选伪代码

```python
def select_high_dl_low_rating(df, pctl=0.80, rate_thr=0.70, min_reviews=100):
    hits = []
    for (platform, category), g in df.groupby(["platform", "category"]):
        thr_dl = g["download_est"].quantile(pctl)
        cand = g[(g["download_est"]   >= thr_dl) &
                 (g["positive_rate"]  <= rate_thr) &
                 (g["rating_total"]   >= min_reviews) &
                 (~g["is_suspect"])]
        cand = cand.copy()
        cand["download_pctl"]     = cand["download_est"].rank(pct=True)
        cand["confidence"]        = (cand["rating_total"] / 500).clip(upper=1)
        cand["opportunity_score"] = (100 * cand["download_pctl"]
                                     * (1 - cand["positive_rate"]) * cand["confidence"])
        hits.append(cand)
    return concat(hits).sort_values("opportunity_score", ascending=False)
```

### 4.5 决策流程

```
读取最新快照 → 按 平台×品类 分组 → 计算 download_est 的 P80 阈值
  → download_est ≥ P80 ?     否 → 剔除（下载不够高）
  → positive_rate ≤ 70% ?    否 → 剔除（口碑尚可）
  → rating_total ≥ 100 ?     否 → 剔除（样本不足 / 低置信）
  → 疑似刷量 ?               是 → 剔除并记 suspect
  → 计算 OpportunityScore → 降序输出「高下载低好评」榜
```

## 5. 页面结构

### 5.1 信息架构

- **首页（列表页）**：全局搜索 · 数据更新时间提示 · KPI 概览 · 筛选栏 · 排序 · 结果列表 · 象限散点图。
- **详情页**：标题区 · 关键指标卡 · 趋势图 · 跨平台对比 · 数据说明区。
- **辅助（P1+）**：关于 / 数据源声明、导出、收藏清单、订阅设置。

### 5.2 首页布局（自上而下）

1. **顶栏**：品牌 + 全局搜索 + 「数据更新时间 + 下次更新时间 + 新鲜度徽章」。
2. **KPI 概览**：覆盖平台数 / 抓取条目数 / 反差命中数 / 平均好评率。
3. **筛选栏（sticky）**：平台多选 · 品类下拉 · 热度门槛（P50/P80/P90）· 好评率上限 · 重置。
4. **视图切换**：「榜单列表」/「我的收藏 N」（徽章显示收藏数量）。
5. **排序切换**：机会指数（默认）/ 热度量级 / 好评率 / 排名 / 更新时间。
6. **结果列表**：☆ 收藏 + 排名 + 条目（图标/名称/开发者）+ 平台标签 + 热度量级 + 好评率（进度条 + 数值）+ 机会指数 + 对比。
7. **我的收藏表**：条目 + 平台 + 热度量级 + 好评率 + 机会指数 + **收藏时间** + 移除；按收藏时间倒序；已不在最新榜单中的条目附「已下榜」标记。
8. **象限散点图**：热度量级（对数）× 好评率，标出目标象限。
9. **分页 / 底部说明**。

> 措辞统一：首页为**多平台混合语境**，指标一律使用中性词「**热度**」（热度量级 / 热度门槛 / 热度 × 好评率），避免在包含 HTML5 网页小游戏时用「下载量」误导；具体量纲（下载量 / 游玩次数）只在**详情页**按平台 `metric_label` 精确展示。

### 5.3 筛选栏规格

| 控件 | 类型 | 字段 | 默认 |
|---|---|---|---|
| 平台 | 多选标签 | `platform_code` | 全部 |
| 品类 | 下拉单选 | `category` | 全部 |
| 热度 | 分档按钮 | `download_pctl` | ≥ P80 |
| 好评率上限 | 滑杆 0–100% | `positive_rate` | ≤ 70% |
| 时间 | 单选 | `stat_time` | 最新 |

### 5.4 排序方式

| 排序项 | 方向 | 场景 |
|---|---|---|
| **机会指数（默认）** | 降序 | 找「高热度低好评」反差机会 |
| 热度量级 | 降序 | 看赛道头部规模 |
| 好评率 | 升序（最低优先） | 快速定位口碑最差者 |
| 排名 | 升序 | 对齐平台原始榜单 |

### 5.5 数据更新时间提示

- 全局顶栏：`数据更新于 2026-10-16 07:05 · 覆盖 2 平台 / 1,200 条 · 下次更新 今日 19:00`
- **新鲜度徽章**：绿（< 12h 正常）/ 黄（12–24h 延迟）/ 红（> 24h 或任务失败）。
- 详情页：`本页数据抓取于 07:05，来源：<平台>公开榜单页`。

## 6. 技术栈与架构

### 6.1 选型（MVP 实际落地）

| 层次 | 选型 | 理由 |
|---|---|---|
| 前端 | 原生 HTML + CSS + JavaScript（零依赖静态站） | 无需构建、无需运行时、双击即可打开 |
| 图表 | 手写 SVG（散点 / 折线） | 避免引入 1MB 图表库，保持站点轻量 |
| 数据交付 | 管道生成 `public/data/latest.js`（全局变量）+ `.json` | **绕开 `file://` 的 CORS 限制**，双击也能跑 |
| 数据管道 | PowerShell + JSON（`pipeline/`） | 云端 runner 与本地开发环境一致（windows-latest + Windows PowerShell），**管道零改造**上云 |
| 调度 | **GitHub Actions 定时任务（cron）**，每日 2 次（北京时间 07:07 / 19:07） | 互联网端无人值守，无需常驻进程，也无需自备服务器 |
| 托管 | **GitHub Pages**（静态托管，站点全程使用相对路径） | 零成本、免运维，推送即发布；天然适配 `/<仓库名>/` 子路径 |
| 归档 | `data/snapshots/*.json` 按时间点留存（云端仅保留最近 6 份） | 可回溯时间序列，同时避免仓库体积膨胀 |

> ⚠️ **已知边界**：GitHub Pages 在国内访问不稳定。若国内访问速度成为硬约束，可迁移到「国内云函数（腾讯云 SCF / 阿里云 FC）+ 对象存储（COS / OSS）静态托管 + CDN」—— 届时只需把管道实现改写为 Node.js / Python（云函数不跑 PowerShell），**前端与 JSON 契约保持不变**。
>
> **升级路径（阶段二起）**：管道迁移到 Python（FastAPI + Playwright + Airflow），前端迁移到 Next.js，数据库用 PostgreSQL 分区表 + Redis 缓存。当前 MVP 的 JSON 契约保持不变，迁移时前端无需改动。

## 7. 数据抓取合规要点

原则：**只抓公开、尊重规则、最小必要、来源可溯、可停可控。**

### 7.1 红线（禁止）

- 禁止绕过登录、付费墙、验证码等技术保护措施获取数据。
- 禁止抓取 `robots.txt` 明确 Disallow 的路径，或服务条款明确禁止抓取的内容。
- 禁止采集、存储任何**用户个人信息**（《个人信息保护法》范畴）。
- 禁止破解、伪造身份，或大规模规避 IP 封禁。
- 禁止整站镜像或批量原样转载平台榜单数据。

### 7.2 应做（Do）

- 数据源优先级：**官方开放接口 / 公开榜单页 / 授权数据** > 页面抓取。
- **先审后用**：每个数据源上线前核对 robots 与 ToS，登记在 `dim_platform.tos_url` 留档。
- **礼貌抓取**：令牌桶限速、限制并发、标识可联系 User-Agent、避开目标站点高峰。
- **来源可溯**：保留 `source_url` / `crawl_at`，页面对外显著标注数据来源。
- **聚合展示**：只展示聚合统计（好评率、排名、数量），**不展示用户评论原文**。
- **最小必要**：主体信息仅用公开的开发者 / 工商信息。
- **可停可控**：保留一键停采开关；提供数据更正 / 删除通道。
- **合规评审**：对外商用前完成法务评审 + 免责声明（仅供参考、不构成投资建议）。

### 7.3 权利与版权边界

| 风险点 | 说明 | 应对 |
|---|---|---|
| 榜单汇编权利 | 编排可能受数据库汇编类权利保护 | 不原样复制排列；经归一化、评分、聚合形成**衍生分析结果** |
| 商标 / 图标 | 权利归原权利人 | 仅作识别用途，不做背书暗示 |
| 用户评价 UGC | 版权属用户 / 平台 | 仅用聚合指标，不展示原文 |
| 反不正当竞争 | 避免贬损特定竞争对手 | 中立数据 + 客观口径，避免误导性结论 |
| 数据留存 | 留存与删除边界 | 原始归档 90 天后转冷存；按权利人要求可删除 |

> **MVP 合规基线：** ① 只抓公开榜单页；② 遵守 robots 与 ToS 并留档；③ 限速 + 可停；④ 页面展示来源、更新时间与免责声明；⑤ 不碰任何个人信息。

## 9. MVP 版本规划

### 9.1 MVP 必做（P0）

| # | 能力 | 落地形态 |
|---|---|---|
| ① | 采集 | 3 个平台（微信 / 支付宝 / **HTML5游戏**）；`demo` 适配器保证开箱即跑，`csv` 适配器对接真实数据，`wechat`/`alipay`/`html5` 适配器按合规开关启用 |
| ② | 清洗 | 名称归一转半角、量纲区间 → `download_est` + `is_estimated`、好评率计算、质量校验 |
| ③ | 评分 | 按「平台 × 品类」算 P80 阈值；`OpportunityScore` 排序 |
| ④ | 展示 | 首页列表页：筛选（平台/品类/热度门槛/好评率上限）+ 排序 + 反差高亮 + 更新时间提示 + **收藏**（☆ 一键收藏、独立表格、记录收藏时间）；详情页：指标卡 + 趋势 + 跨平台对比 |
| ⑤ | 更新 | `pipeline\run.ps1` 全流程 + GitHub Actions 定时任务每日 **2 次**（北京时间 07:07 / 19:07） |
| ⑥ | 合规 | 页面数据来源、更新时间、估算标记与免责声明 |

### 9.2 暂不做（P1 / P2）

用户账号体系、收藏 / 订阅推送（P2）；跨平台合并去重、更多平台与品类（P1）；CSV 导出、后台可视化配置（P1）；支付与商业化（远期）。

### 9.3 MVP 判定标准

连续 7 天每日 2 次自动更新成功；榜单可一键筛选出反差名单；人工抽检准确率 ≥ 80%；首页首屏 < 2s。达成即可对外小范围试用。

### 9.4 阶段路线

| 阶段 | 目标 | 范围 |
|---|---|---|
| 阶段一（MVP） | 跑通「采集 → 清洗 → 筛选 → 展示 → 每日 2 次更新」闭环 | 3 平台（含 HTML5 网页小游戏）· 列表页 + 详情页 · 基础筛选（**当前已实现**） |
| 阶段二 | 提升洞察深度与覆盖 | 5 平台 · 跨平台合并去重 · CSV 导出 · 趋势分析 |
| 阶段三 | 产品化与商业化探索 | 账号 / 收藏 / 订阅推送 · 后台配置化 · 更多品类 |

## 10. MVP 总结（一句话）

**先做「3 个平台（微信 / 支付宝 / HTML5网页小游戏）+ 每日两次流水线 + 一个反差榜单页」。** 把「采集 → 清洗 → 筛选 → 展示 → 自动更新 → 合规声明」这条最小闭环跑稳，用真实数据验证「高热度低好评」名单是否真有价值；其余功能都等闭环跑通、数据积累后再迭代。

## 附录 A · 术语表

| 术语 | 含义 |
|---|---|
| 反差样本 | 热度高但好评率低的条目（小程序 / HTML5 网页小游戏） |
| 机会指数 | `热度分位 × (1 − 好评率) × 置信度`，0–100 |
| 分位 | 同平台同品类内的相对排名位置 |
| 量纲（metric_label） | 平台热度的计量口径：小程序为「下载量」，HTML5 网页小游戏为「游玩次数」；首页混合展示时统一称「热度」 |
| 置信度 | 由评价样本量推导的可信程度 |
| 快照 | 某一次更新时点的完整榜单数据 |
